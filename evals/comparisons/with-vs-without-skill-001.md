# With-Skill vs Without-Skill Structural Comparison — Run 001

Date: 2026-08-29
Plan: `.plans/with-vs-without-skill-comparison.md` r1 (approved)
Method: one independent baseline design per published case, generated by a fresh agent from the canonical `case.json` requirement brief only; each baseline scored blind by a separate judge agent against the case's own `expected`/`forbidden` assertions; coordinator synthesis against the already-reviewed Skill outputs.

This document is eval-suite meta-evidence. It is not linked into the published Pages catalog and does not modify any case fixture, frozen spec, or runtime.

## Evidence limits (read first)

- **n=1 per case.** One baseline run per case; no variance estimate.
- **Same-model-family confound, both directions.** Baseline designers, blind judges, and the Skill-side generation all come from the same model family. A strong baseline may reflect model prior rather than proof the Skill adds nothing; a weak baseline may reflect prompting rather than absence of the Skill.
- **Spec-level only.** Baselines are design documents, not runnable prototypes; behavioral comparison (real operation) was out of scope for this first pass.
- **Not independently reviewed.** Baseline scoring is independent (blind judges); the final comparison synthesis is coordinator self-review.
- **Judge blindness is asymmetric by design.** Judges saw the rubric and the baseline doc, not the case brief's `current_state` narrative. One scoring artifact resulted and is annotated per case.

## Contamination check

All four baseline outputs were scanned for Skill vocabulary (`problem state`, `capability space`, `anti-average`, `access path` as jargon). No contamination found. Terms shared with case fixtures (e.g. "capability catalog" in 002, "access paths" in 003) originate from the `case.json` brief text itself, which was given verbatim. No baseline agent reported or showed evidence of reading the repository or any skill file.

## Case 001 — Bulk Assignment

### Blind score sheet (judge-001, verbatim verdicts)

EXPECTED: E1 PASS, E2 PASS, E3 PASS, E4 PARTIAL, E5 PASS, E6 PASS, E7 PARTIAL.
FORBIDDEN: F1 PASS, F2 PASS, F3 PASS, F4 FAIL, F5 PARTIAL, F6 PASS.

Judge's core deduction: the touch-side "确认指派给 X" button contradicts the document's own "不设独立确认步" principle, simultaneously hurting E4 (commit without redundant confirmation), E7 (presentation may differ without changing semantics), and F4 (unnecessary confirmation present).

### Structural difference vs Skill output

The Skill output (frozen `prototypes/assignment/interaction-spec.md`, reviewed in `structural-review.md`) commits technician selection **immediately on both pointer and touch** — "Technician selection commits immediately. No additional Apply/Confirm stage exists because no new required uncertainty would be resolved by it." Platform adaptation changes the container only (anchored Popover on pointer via `touchable` capability media, Sheet on touch); the commit semantics never fork.

The baseline independently arrived at the same single-question, no-re-ask, undo-instead-of-confirm structure — and then **re-introduced a confirmation stage exactly where platform pressure was applied** (touch "误触成本更高" reasoning). This is the specific failure mode the Skill's shared-semantics decision exists to block: a plausible-sounding platform rationale ("touch needs more confirmation") silently forking task semantics. The without-Skill designer, reasoning freely, produced it in the only place the rubric could catch it.

Baseline additions beyond fixture scope (partial-failure handling, grouped technician suggestions) are competent product thinking, not structural differences.

## Case 002 — Merge Command Contract

### Blind score sheet (judge-002, verbatim verdicts)

EXPECTED: 8/8 PASS. FORBIDDEN: 6/6 PASS.

### Structural difference vs Skill output

No scored failures. Three strictness-level differences remain visible to direct comparison:

1. **Suggested-default primary.** The baseline pre-selects the more complete record and labels it "建议", partially resolving the one decision the fixture leaves unresolved. The Skill output proceeds to the primary-record question with both options symmetric — the single remaining decision stays fully user-owned.
2. **Separate commit button.** The baseline commits via an explicit "合并联系人" primary button after the primary choice (panel-as-confirmation-surface). The Skill output commits **directly on primary selection** ("selecting the primary record commits directly and exposes Undo") — one fewer step, with Undo carrying recoverability. The blind judge accepted the baseline's button as non-redundant (the panel itself resolves new information: field comparison); the Skill reading of "commit after the primary record is chosen" is stricter.
3. **Field-merge preview.** The baseline adds per-field diff cards and a merged-field-count preview. Competent, and arguably good product design, but it adds a scanning task before the one unresolved question; the Skill output exposes only what the primary-record decision needs.

Framing: this case shows the model prior can satisfy the full rubric without the Skill. The remaining differences are about *how strictly* "only the unresolved decision" is interpreted — exactly the dimension a rubric of this size under-measures.

## Case 003 — Move Access Paths

### Blind score sheet (judge-003, verbatim verdicts)

EXPECTED: 7/7 PASS. FORBIDDEN: 6/6 PASS.

### Structural difference vs Skill output

Structurally near-identical to the Skill output: destination asked only on the command path, drop target answers the drag path, shared After state/Toast/Undo, invalid drop as silent no-op, touch keeps the command path without an invented drag presentation.

**Fixture-quality finding (more important than the score):** the case.json `current_state` states the resolution outright — "a valid drag onto a specific depot has already supplied the destination through the drop target" — and `input.unresolved` spells out "Drag path after a valid drop: no destination question remains." A competent designer given this brief cannot plausibly fail E3/F1. Case 003 as currently fixtured has low discriminating power for with/without-Skill comparison; the convergence here is evidence about the fixture, not about the Skill's marginal value.

Follow-up candidate (later alignment cycle, out of scope here): rewrite the 003 brief to describe the *team's consistency desire* without naming the resolution, so the baseline must derive the asymmetry itself.

## Case 004 — Media + Template Composer

### Blind score sheet (judge-004, verbatim verdicts)

EXPECTED: E1 PASS, E2 PASS, E3 PASS, E4 PASS, E5 PASS, E6 PASS, E7 FAIL, E8 PARTIAL.
FORBIDDEN: F1 FAIL, F2 PASS, F3 PASS, F4 PASS, F5 PASS, F6 PASS, F7 PASS, F8 NA, F9 PASS.

### Coordinator annotations to the score sheet

- **F1 re-scored to PASS (judge mis-score).** The judge flagged "All templates" and "Text image" as real branded template names. Both strings are the fixture's own genericized labels, present verbatim in the case.json `current_state` the baseline was given ("generic entries such as All templates and Text image"). The forbidden item targets the real application name and distinctive real-brand template names, which appear nowhere in the baseline. Cause: judges were blind to the brief narrative by design; the rubric item was not self-contained. Recorded as a rubric-authoring lesson, not a baseline defect.
- **E7 FAIL / E8 PARTIAL / F8 NA are process assertions, not interaction-structure assertions.** They test frozen-baseline discipline, source-vs-inference separation, and comparison methodology — properties of an eval *process* that a one-shot design document cannot exhibit. Scoring them against a spec-level baseline measures the comparison method, not the baseline's design quality. This is itself a finding: part of the Skill's contribution (frozen current-state reconstruction, AVG-023 surface purity, evidence separation) is invisible at spec level.

### Structural difference vs Skill output

Both sides keep the full capability set (Album, Video, Game assets, All templates), keep the draft visible, reuse draft context in template flows, and protect direct-media paths. The differences are in **what the first question is** and **when help appears**:

| Axis | Without-Skill baseline | Skill optimized output |
|---|---|---|
| First question | Source taxonomy, preserved: four peer tabs + minimized quickbar (`相机 · 相册 · 视频 · 游戏素材 · 模板`) | Problem state: `添加配图` → 从已有素材 / 根据正文生成 / 浏览创意模板; source taxonomy resolved one level later, only where undecided |
| Template discovery | Improved *inside* the catalog: recommendation row (`为你的草稿生成`) on entering the template tab + grouped browsing | Surfaced *outside* the catalog: draft-illustration intent is a first-class entry; narrow intent never opens the broad catalog |
| Proactive help | None (attachment entirely user-initiated) | Contextual suggestion `给这段内容配张图` gated on a modeled natural break, nonblocking, dismissible |
| Generation result | Insert-at-cursor after `生成` | Provisional candidates (`选择一个候选` + `重新生成`); explicit `插入正文` commit; draft never modified |
| Permission friction | Ghost card inside grid (a genuine improvement over the banner) | Unchanged from baseline (friction preserved as product reality, not redesigned away) |

The baseline's improvements are real but all live **within the existing taxonomy**: a user holding a finished draft must still recognize that the template *tab* is where draft-derived visuals live. The Skill output removes exactly that recognition step. This mirrors the Case 004 frozen-baseline finding (`evals/cases/004-media-template-composer/comparison.md`, axis 1: discoverability) from the opposite direction: asked to improve the composer, the without-Skill designer optimized the catalog; the Skill re-sequenced the question order.

## Cross-case findings

1. **The model prior is strong at this abstraction level when the brief pre-digests the structure.** Cases 002 and 003 scored perfect rubrics without the Skill. The case.json `known`/`unresolved` fields themselves encode the central structural insight; a designer handed them is already holding the answer. Future comparison runs should use rawer problem statements (user complaint + context, no known/unresolved decomposition) to measure what the Skill's decomposition step contributes.
2. **Baseline failures concentrate exactly where the Skill carries explicit guards.** The only scored structural failure across all four cases (001 F4) is confirmation creep under platform pressure — the pattern the Skill's "presentation may differ, semantics stay shared" rule exists to prevent. The largest unscored difference (004) is taxonomy-first vs problem-state-first — the Skill's "resolve genuinely unresolved questions in order" discipline.
3. **Process value is invisible at spec level.** Frozen baselines, evidence separation, and surface purity (AVG-023) do not appear in any one-shot design document. If these are to be compared, the comparison needs a process-level protocol (e.g. asking the without-Skill side to produce the full eval artifact, not just a design).
4. **Fixture hardening:** case 003's brief is nearly self-answering (see case section); case 004's rubric mixes interaction assertions with process assertions and one non-self-contained forbidden item (F1) — both are fixture-quality improvements for a later cycle.

## Follow-ups (not in this scope)

- Multi-run baselines (n≥3 per case) and at least one different model family, to bound the n=1 and same-family confounds.
- Rawer brief format for a second comparison run.
- Runnable baseline prototypes for behavioral comparison, if the spec-level signal from a second run justifies the cost.
- Fixture revisions for case 003 (brief) and case 004 (rubric separation), each via its own alignment cycle.

### A.2 Case 002 baseline (agent baseline-002)

> **Structure summary**: contextual action bar with Merge → focused Merge Sheet (modal/bottom sheet) with side-by-side field-diff cards → one question: primary record (binary choice, completeness-based default marked "建议", live result preview) → explicit "合并联系人" primary button → atomic commit with loading state, dismissal blocked mid-commit → result row highlight + Toast with Undo (6s) + "最近操作" re-entry → snapshot silent and automatic; conflict strategy default union, collapsed "高级选项"; minimum path 4 steps.

### A.3 Case 003 baseline (agent baseline-003)

> **Structure summary**: "拖拽落点即答案" — Depot Picker appears only when destination unresolved → command path: Move button → pending-highlight → picker (current depot pinned/disabled) → tap depot = immediate commit → drag path: ghost placeholder + legal-drop highlighting → valid drop commits directly, invalid drop rebounds silently → shared After: 250ms migration animation + Toast with Undo (Cmd/Ctrl+Z, ~10s window) → touch: no drag (scroll conflict), command path only with bottom-sheet picker.

### A.4 Case 004 baseline (agent baseline-004)

> **Structure summary**: three-layer persistent layout (context bar / draft editor ≥60% / acquisition panel collapsible to quickbar `相机·相册·视频·游戏素材·模板`) → direct media unified: select → insert at cursor anchor → panel auto-collapses; permission banner demoted to in-grid ghost card → templates: `为你的草稿生成` recommendation row (draft title/body/topics) + grouped browsing (functional vs themed generators) → in-panel config form, draft-known fields prefilled, only unknowns asked, defaults skippable, live preview → generate → insert at cursor / regenerate; results banked per-draft for re-insert → draft never leaves screen; anchor memory; no source or template family removed.
